## 1. Concrete approval scope

Approved local target: **`e2e_v3_step13_capacity_20261003_a`**, a new database on the existing fictional PostgreSQL 17 test container at `127.0.0.1:5433`. Use a **new Redis 7 test container on `127.0.0.1:6381`**, with a capacity-specific `ts-starter:e2e:` prefix. The capacity API owns `127.0.0.1:3013` and uses production mode, fictional auth configuration, paused courier workers and blank external credentials. Neither merchant data nor the retained Step 10 correctness DB is a target.

Approval must explicitly cover:

1. Creating the separate local capacity DB/Redis resources, applying **existing** migrations to that new DB, and provisioning verified fictional auth/RBAC users. No schema changes, resets, production queries, or normal merchant seeding are part of this proposal.
2. Applying the bounded dataset: 10,000 customers, 25,000 orders, 1,000 products, 3,000 variants and the related rows below.
3. A temporary **isolated-headroom** app limit policy: public 10,000/minute; admin, protected and special 1,000/minute. Limits remain enabled; auth limits remain unchanged. The runner restores the original settings or deletes its own new settings row during cleanup. These numbers are only for the single-IP synthetic capacity target; do not deploy them to shops or treat them as proxy/security acceptance.
4. Smoke (one 17-request journey), data-volume (20 iterations of 16 public/admin reads), expected (25 public + 2 admin + 1 checkout requests/second for 15 minutes), peak (100 public + 5 checkout requests/second for two minutes), and soak (10 public + 0.2 checkout requests/second for 60 minutes). At most 260 allocated VUs across expected scenarios, 240 at peak/soak; allocation is not measured concurrency or achieved throughput.
5. Read-only before/after correctness checks and resource monitoring during these local runs. Preserve ignored reports and fictional resources for review; no automatic DB deletion/reset or commits.

Step 13 point 4 requires “user execution or explicit expanded authorization.” An environment flag records approval; setting it is not approval by itself. Staging and backup/restore need separate approval. No real courier booking is allowed by this capacity scope.

## 2. What is prepared

- `tests/load/capacity-dataset.ts`: pure deterministic data builder; never connects to DB. Fixed maximum dataset bounds and run ID format; separate IDs by run; fictional `.example.test` addresses. Active/draft catalog, all five fulfillment kinds, warranty/serial only for gadgets, two warehouses, expiring food batches, movements, reservations, receipts, partial payments, refunds, discounts, food bookings, gadget units/allocations/warranty claims, visitor sessions and activity rows.
- `tests/load/generate-step13.ts`: defaults to a full **dry run without DB access**. Applying requires `--apply`, prior approval flag, exact approved capacity DB name, run ID and a verified fictional actor. It dynamically imports the DB client only after guards. It requires empty commerce/analytics/provider/settings tables, permits separately provisioned auth/RBAC, writes batches of at most 100, and does not resume/reset/delete. A partial failure leaves an isolated DB to inspect; obtain an explicit new-target/cleanup decision rather than retrying automatically. Run with the app stopped and only one generator/operator to avoid concurrent writes after the empty checks.
- `tests/load/step13-k6.js`: public catalog/search/detail/facets, authenticated order/customer/product list/detail, inventory/movements, visitors/activity and COD checkouts. Fresh-food checkouts carry the generated slot. Every execution gets new checkout keys. Peak/soak intentionally have no admin scenario/threshold. No headers spoof customer IPs, no external script imports or result upload.
- `tests/load/run-step13.ts`: requires exact capacity DB and approved headroom policy; checks counts and baseline consistency; owns its compiled API; validates the fictional session; runs k6 with a whitelisted environment and an empty local config, telemetry disabled. No inherited cloud token/output configuration. Restores rate settings, stops owned API, disconnects clients. A profile uses unique report/checkout execution IDs, so repeated profiles cannot silently replay the prior run's checkouts.
- `tests/load/check-step13-invariants.ts`: receipts/reversals/refunds and payment status, checkout keys, movement-to-stock and reservation-to-reserved counters, food bookings/capacity, discount counters/limits, active shipment/provider identities, durable order/operation preservation, queues and expired leases. Successful checkout count must equal newly persisted orders. It is read-only and caller-guarded. It does not establish real provider-side uniqueness or execute fulfillment transitions.
- `tests/load/capacity-metrics.ts`: five-second non-overlapping samples of API RSS/CPU ticks/FDs, local hardware/cgroup limits, target DB connections/lock waits/transaction counters, selected Redis memory/client/error counters and queue age/state/expired leases. Sampling errors reject acceptance. These observers contribute overhead and measure shared resources unless deployment isolation is separately established. CPU ticks are counters, not a calculated utilization percentage. Operators still interpret trends and saturation; there is no automated production alerting service.

The dry-run report contains 17,500 receipts, 2,500 partial refunds, 25,000 reservations, 48,000 stock movements, 5,001 food bookings, 5,000 discount redemptions, 9,466 gadget units, 3,466 allocations, 432 warranty claims, 10,000 visitor sessions and 25,000 activity rows. Synthetic distribution is reviewable and deliberately bounded; it is not observed shop traffic. Courier workers are paused and no shipment backlog is generated: this workload does not certify courier throughput or simulator compatibility.

## 4. Operator procedure after explicit approval

1. Record approval and exact target identity. Stop if that name already exists or any environment matches development/production. Create the new approved resources and apply existing schema under that approval; this guide intentionally provides no DB CLI commands.
2. Prepare ignored mode-0600 `capacity.env`: `NODE_ENV=test`, `E2E_MODE=true`, approved local DB/Redis URLs, a separate `ts-starter:e2e:` Redis prefix and `STEP13_CAPACITY_DATABASE` equal to the exact approved DB name. Never print URLs containing credentials. Provision verified fictional owner/RBAC using the reviewed isolated test workflow, not merchant seeds or a live mailbox.
3. Review the generated distribution. Set a unique `STEP13_FIXTURE_RUN_ID`, actual fictional `STEP13_FIXTURE_ACTOR_ID`, and explicit `STEP13_FIXTURE_BASE_TIME` for reproducibility. Set `STEP13_FIXTURES_APPROVED=true` only after approval. Run `bun --env-file=tests/artifacts/step13/capacity.env tests/load/generate-step13.ts --apply`. Inspect counts and successful invariants; leave generated `capacity-fixtures-<run>.json` ignored and mode 0600. The script requires empty commerce/analytics, creates no auth users and leaves its session cookie blank.
4. Build the reviewed compiled API with the same controlled production-local environment and current source. Existing `tests/artifacts/step13/api` was produced by the runtime smoke; record its build/source revision and rebuild if runtime code changed. Do not run root wrappers that inject unrelated test env. A source commit hash alone does not identify uncommitted builds; preserve a source/build fingerprint.
5. Authenticate the fictional owner on this capacity API using the shared `step13ProductionEnv` configuration and save its production-compatible session cookie in the ignored generated manifest. Stop that temporary API before the load runner. The owner must have permissions for all admin reads; matching an email alone is not proof of RBAC. Never copy a real shop cookie. The runner checks authenticated email/verification before k6; smoke/admin checks establish actual route access.
6. In the approved capacity env, set `STEP13_LOAD_APPROVED=true`, `STEP13_LOAD_LIMIT_POLICY=isolated-headroom`, `STEP13_LOAD_TARGET=http://localhost:3013`, `STEP13_LOAD_FIXTURES` to the generated ignored manifest and `STEP13_K6_BINARY` to the reviewed local tool. Set `STEP13_LOAD_PROFILE=smoke`; run `bun --env-file=tests/artifacts/step13/capacity.env tests/load/run-step13.ts`. Only proceed if all functional/resource/invariant checks pass.
7. Run `volume` next. Inspect response statuses and individual tagged endpoints; aggregate latency cannot hide a slow customer detail or facet query. Then run `expected`, `peak`, and `soak`, in that order, under the recorded approval. Investigate any failure before increasing load or making a capacity claim. Do not run profiles simultaneously.
8. Inspect uniquely named `capacity-<run>-<profile>-<execution>.json`, `invariants-...json` and `resources-...json`. Confirm HTTP failures <1%, all business checks, no dropped iterations, p95 catalog <500ms/admin <750ms/checkout <1500ms, p99 checkout <3000ms, no new stale leases/lost rows/counter mismatch and checkout count reconciliation. Review RSS/connection/lock/Redis/backlog trends for bounded use. Snapshot actual approved limiter config, target versions and monitoring interpretation in the evidence.
9. Confirm API stopped, original rate settings restored and other retained local services unchanged. A SIGKILL/crash can interrupt restoration; inspect only the approved capacity target before another run. Keep artifacts private and resources retained for review. No automatic reset, cleanup of another DB, commit, live courier or tutorial recording follows.
10. Update the V3 ledger with actual results and explicit failed/pending checks. Staging HTTPS/proxy/auth limits, production worker/simulator recovery, deployed monitoring and user-controlled credential/backup restore checks still remain. Three later numbered steps (14–16) remain; Step 13 is complete only after its acceptance evidence is reviewed.
